# setup-analytics: 정적 사이트에 GA4 연결하기

배포된 정적 사이트에 구글 애널리틱스 4를 붙이는 순서다. 코드 점검 → GA 속성 만들기(Chrome) → Cloudflare에 측정 ID 넣고 다시 배포 → 수집 확인 → 문서 기록으로 진행한다.
배포 자체(Cloudflare 프로젝트 만들기, 캐시 헤더 등)는 `conan-web:deploy-cloudflare` 스킬이 맡는다. 아직 배포 전이면 그 스킬부터 쓰자고 안내한다.

## 기본 원칙

- **사용자에게 하는 말은 모두 한국어로 쓴다.** 짧은 진행 안내, 마무리 요약, 질문 버튼 문구까지 전부다. 사용자는 한국어 사용자이고 영어가 섞이면 크게 불편해한다.
- **계정과 권한에 관한 결정은 사용자가 한다.** 어느 구글 계정에 만들지, 새 GA 계정의 약관 동의, 구글·GitHub 본인 확인(2단계 인증)은 사용자에게 맡기고 기다린다. 비밀번호나 인증 코드를 대신 입력하지 않는다.
- **사이트에 공개되는 수집 범위는 개인정보처리방침과 맞춘다.** 방침에 "이미지 내용이나 파일 이름은 보내지 않는다"고 썼다면, 그런 값을 자동으로 보낼 수 있는 GA 기능은 끈다. 방침과 실제가 다르면 신뢰와 법적 문제가 생긴다.
- **측정 ID는 공개되는 값이라 코드나 환경 변수에 넣어도 된다.** 다만 GA 관리자 권한, API 비밀번호(Measurement Protocol API secret)는 저장소에 넣지 않는다.

## 0. 코드 점검 (Chrome을 열기 전에)

GA를 만들기 전에, 사이트가 측정 ID를 받으면 제대로 동작하는지 먼저 본다. 여기서 문제가 있으면 GA를 만들어도 수집이 안 되거나 방침과 어긋난다.

1. **측정 ID를 어디서 받는지** 찾는다. 프레임워크마다 다르다.
   - Next.js: `NEXT_PUBLIC_GA_ID` 같은 환경 변수(빌드 때 페이지에 들어감)
   - Astro: `src/site.config.js`의 `gaId` 같은 설정 값(코드에 직접) 또는 환경 변수
   - Vite: `VITE_GA_ID` 환경 변수 또는 `index.html`에 직접
   설정 값이 코드에 있는 구조면 Cloudflare 환경 변수 대신 코드를 고치고 push한다.
2. **값이 없을 때 스크립트를 넣지 않는지**, 있을 때 `gtag/js?id=<ID>`와 `gtag('config', <ID>)`가 들어가는지 확인한다.
3. **동의 기본값**: GA와 애드센스 중 하나라도 켜지면 들어가는지, 두 스크립트보다 앞에 있는지 확인한다. 동의 코드가 GA 블록 안에만 있으면 애드센스만 켰을 때 빠진다. 코드 예시는 `conan-web:deploy-cloudflare`의 `references/adsense-checklist.md` "동의 기본값 예시"에 있다.
4. **보내는 이벤트와 방침 비교**: 코드에서 `track(`, `gtag('event'`를 찾아 이벤트와 값 목록을 만들고, 개인정보처리방침의 수집 항목과 맞는지 본다. 파일 이름, 이미지 내용, 이메일 같은 값이 이벤트에 들어가면 안 된다. 이 목록은 1단계에서 맞춤 측정기준을 등록할 때도 쓴다.
5. **링크 클릭 리스너**: 링크 클릭을 한꺼번에 기록하는 코드(`closest('a[href]')` 같은 위임 리스너)가 있으면, 결과 다운로드 링크(`a[download]`, `blob:` 주소)를 빼는지 본다. 빼지 않으면 다운로드마다 임의 UUID 주소가 `link_click`으로 쌓이고 `download` 이벤트와 중복된다.
6. **방침의 보관 기간**: 개인정보처리방침에 적힌 GA 보관 기간(예: "최대 14개월")을 메모해 둔다. GA4 기본 보관 기간은 2개월이라 1단계에서 맞춰야 한다.

문제가 있으면 GA를 만들기 전에 보고하고, 고칠지 묻는다.

## 1. GA 속성과 웹 스트림 만들기 (Claude in Chrome)

자세한 화면 순서와 막히기 쉬운 곳은 [references/ga4-console.md](references/ga4-console.md)를 읽는다. 요약:

1. **계정 확인**: Chrome에는 구글 계정이 여러 개 로그인되어 있을 수 있다. analytics.google.com을 열고 오른쪽 위 프로필에서 지금 계정을 확인한다. 어느 계정에 만들지 사용자에게 묻는다(기존 사이트들의 GA가 있는 계정이 대개 맞다). 계정을 바꿀 때는 주소에 `?authuser=<email>`을 붙인다.
2. **이미 GA 계정이 있으면 속성만 추가**한다(약관 동의 없음). 관리 → 만들기 → 속성. GA 계정 자체가 없으면 새 계정의 약관 동의는 사용자가 직접 해야 하므로 그 화면에서 멈추고 안내한다.
3. **속성 설정**: 속성 이름은 서비스 이름, 보고 시간대는 대한민국(GMT+09:00), 통화는 애드센스를 쓸 거라면 미국 달러로 둬도 된다. 업종·규모·목표는 서비스에 맞게 고른다(작은 웹 도구면 "인터넷 및 통신", "작음", "웹 트래픽 파악"과 "사용자 참여").
4. **웹 스트림**: 플랫폼 "웹", 주소는 실제 배포 주소(`<project>.pages.dev` 또는 연결한 도메인), 이름은 "<서비스> 웹".
5. **향상된 측정 조정**: 톱니바퀴를 눌러 항목을 본다. 페이지 조회의 고급 설정 "브라우저 기록 이벤트 기반 페이지 변경"은 켜 둔다. Next.js·Astro처럼 사이트 안 이동이 새로고침 없이 일어나는 사이트는 이 설정이 있어야 두 번째 페이지부터 조회가 잡힌다(코드가 첫 로드에만 `config`를 부르는 경우). 기본적으로 **파일 다운로드**와 **양식 상호작용**은 끈다. 파일 다운로드는 내려받은 파일 이름(`file_name`)과 링크를 보내고, 양식 상호작용은 양식 이름과 ID를 보낸다. 방침이 이것을 허용하지 않거나, 사용자가 올린 파일을 다루는 도구라면 특히 꺼야 한다. 사이트 안 검색이 없으면 사이트 검색도 꺼도 된다.
6. **데이터 보관 기간**: 관리 → 데이터 수집 및 수정 → 데이터 보관에서 이벤트 데이터 보관을 개인정보처리방침에 적은 기간(대개 14개월, 무료 GA4의 최댓값)으로 바꾸고 저장한다. 기본값 2개월로 두면 방침과 실제가 다르고, 두 달 지난 탐색 보고서가 비게 된다.
7. **사용자 제공 데이터 수집**: 관리 → 데이터 수집 및 수정 → 데이터 수집에서 "사용자 제공 데이터 수집"이 꺼져 있는지 본다. 켜면 이메일·전화번호 같은 값을 자동으로 찾아 보낼 수 있어, 개인 정보를 받지 않는다고 쓴 방침과 맞지 않는다. 바꾸지 말고 상태만 확인해 보고하고, 켜져 있으면 끌지 묻는다.
8. **맞춤 측정기준**: 0단계에서 모은 이벤트 매개변수(예: `scale`, `backend`, `format`) 가운데 보고서에서 나눠 보고 싶은 것을 관리 → 데이터 표시 → 맞춤 정의 → 맞춤 측정기준 만들기(범위: 이벤트)로 등록한다. 등록 전에 들어온 데이터에는 적용되지 않으므로 처음에 해 두는 것이 좋다. 무엇을 등록할지는 사용자에게 목록을 보여 주고 고르게 한다.
9. **측정 ID 읽기**: 스트림 세부정보의 "측정 ID"(`G-`로 시작)를 읽는다. 화면 글꼴에서 숫자 0과 영문 O가 비슷하므로 스크린샷으로 읽지 말고 페이지 텍스트에서 정규식(`/G-[A-Z0-9]{8,12}/`)으로 뽑고, 필요하면 글자 코드로 확인한다.

## 2. 측정 ID 넣고 다시 배포

[references/cloudflare-env.md](references/cloudflare-env.md)를 읽는다. 요약:

1. Cloudflare 대시보드 → Workers & Pages → 프로젝트 → **Settings → Variables and secrets → Add**에서 측정 ID 변수를 추가하고 저장한다. 종류는 Text(공개 값)다.
2. 환경 변수는 **다음 배포부터** 들어간다. **Deployments → 최신 배포의 "…" → Retry deployment**로 다시 배포하거나, 문서 커밋을 push해서 다시 배포한다(push는 사용자 승인).
3. 설정 파일에 값을 넣는 구조(Astro `site.config.js` 등)라면 코드를 고치고 커밋한 뒤 사용자 승인을 받아 push한다.

## 3. 수집 확인

1. 배포가 끝나면 [scripts/check_ga.py](scripts/check_ga.py)로 실제 사이트를 확인한다.
   ```bash
   python3 <skill-dir>/scripts/check_ga.py https://<site> --id G-XXXXXXXXXX [--path /about ...]
   ```
   측정 ID가 들어갔는지, 동의 기본값이 있는지, 동의 기본값이 GA·애드센스 스크립트보다 앞에 있는지를 페이지마다 표로 보여 준다. 배포가 아직 진행 중이면 옛 페이지가 나오므로 몇 번 다시 확인한다.
2. Chrome으로 사이트 페이지를 하나 연 뒤, GA의 **실시간 개요**(`#/a<계정>p<속성>/realtime/overview`)에서 방금 연 페이지 조회가 잡히는지 본다. 일반 보고서는 24~48시간 걸리므로, 실시간에 보이면 연결은 된 것이다.
3. 향상된 측정 설정은 GA 화면(스트림 → 향상된 측정 톱니바퀴)에서만 확인한다. 공개 태그 파일(`gtag/js?id=…`) 안의 `vtp_enableDownload`, `vtp_enableForm` 같은 값은 화면에서 끈 뒤에도 `true`로 나와서 실제 설정을 나타내지 않는다(2026-11 PixelUp에서 확인).
4. 실시간에 안 보이면: 광고 차단 확장, 측정 ID 오타(0과 O), 배포 전 페이지, 동의 기본값으로 분석 쿠키가 막힌 지역(EEA 등)인지 순서대로 확인한다.

## 4. 기록과 보고

- 프로젝트의 `DEPLOY.md`(없으면 만들지 묻기)에 측정 ID, GA 계정·속성 이름, 향상된 측정에서 끈 항목과 이유, 확인 날짜를 적는다. 다음에 다시 조사하지 않게 하려는 것이다.
- 개인정보처리방침에 Google Analytics가 위탁·수집 항목으로 적혀 있는지 확인한다. 없으면 고칠 것으로 보고한다.
- 사용자에게는 아래를 한국어로 짧게 보고한다: 만든 속성과 측정 ID, 끈 항목과 이유, 보관 기간과 등록한 맞춤 측정기준, 확인 결과(사이트 코드, 실시간 보고서), 남은 일(일반 보고서는 하루 뒤, 애드센스 연동 등).
- 선택 사항으로 안내할 것: 운영자 본인의 방문을 빼는 "내부 트래픽" 정의(관리 → 데이터 스트림 → 태그 설정 구성 → 내부 트래픽 정의, 그리고 데이터 필터 활성화).
- 브라우저에서 연 탭은 사용자가 보겠다고 하지 않는 한 닫는다.
