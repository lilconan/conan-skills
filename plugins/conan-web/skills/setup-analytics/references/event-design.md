# 이벤트 설계: 사용자 행동을 GA4로 보내기

"버튼마다 이벤트를 붙인다"가 아니라 **답하고 싶은 질문**에서 출발한다. 질문이 없는 이벤트는 보고서만 어지럽히고 GA 한도(이벤트 이름 500개, 이벤트 범위 맞춤 측정기준 50개)를 쓴다.

## 1. 순서

1. 화면에서 사용자가 할 수 있는 동작을 모두 모은다: `onClick`, `onChange`, `onDrop`, 링크, 슬라이더, 키보드.
   - 사용자가 "다른 프로젝트처럼 버튼 같은 것도 GA에 보내?"라고 물으면, 두 프로젝트에서 보내는 이벤트를 각각 찾아(`grep -rn -o -E "track\(\"[a-z_]+\"" src components lib`, `gtag('event'`) 영역별로 나란히 비교한 표를 먼저 보여 준다.
   - 이미 보내는 이벤트의 값이 GA 맞춤 측정기준으로 등록돼 있는지도 확인한다. 등록되지 않은 값은 보고서에서 나눠 볼 수 없다(PixelUp은 처음에 하나도 등록되어 있지 않았다).
2. 서비스 운영에 필요한 질문을 적는다. 도구 사이트에 흔한 질문:
   - 이 브라우저·기기에서 도구를 쓸 수 있나? → 방문마다 한 번 `tool_ready`(기능 지원 여부)
   - 어떻게 넣나, 왜 거부되나? → `add_*`(방법·형식·크기 구간), `*_rejected`(이유)
   - 어떤 설정을 쓰나, 어떻게 시작하나? → `*_start`(설정, 단일·일괄)
   - 충분히 빠른가, 예상 시간이 맞나? → `*_done`(걸린 시간, 예상 시간, 첫 실행 준비 시간)
   - 무엇이 왜 실패하나, 언제 포기하나? → `*_failed`(이유 분류), `*_cancel`(시점)
   - 결과를 확인하고 받아 가나? → 결과 비교·미리보기 첫 조작, `download`
   - 결과를 받지 않고 떠나나? → 떠날 때 한 번 `session_summary`(beacon)
   - 부가 기능을 쓰나? → `batch_action` 같은 묶음 이벤트(action 값으로 구분)
   - 콘텐츠가 도구로 이어지나? → 링크 클릭의 위치(`data-track-area`), 예시 조작
3. 질문마다 이벤트 하나, 값은 질문에 답하는 데 필요한 만큼만 정한다. 비슷한 동작은 이벤트를 늘리지 말고 `action` 같은 값으로 묶는다.
4. 사용자에게 "질문 → 이벤트 → 값" 표로 보여 주고 고르게 한다. 가장 가치 있는 것(기능 지원 여부, 거부 이유, 속도, 받지 않고 떠남)을 먼저 표시한다.

## 2. 규칙

- **개인정보:** 파일 이름, 이미지·오디오 내용, 정확한 크기, 입력 텍스트, 오류 원문은 보내지 않는다. 크기는 구간(`~256`, `~512`, `~1024`, `~2048`, `>2048`), 오류는 분류(`memory`, `network` …)로 바꾼다. GPU 모델명처럼 기기를 특정할 수 있는 값도 빼고 "지원 여부"만 보낸다.
- **이벤트 이름·값:** snake_case 영어, 동사_대상 꼴(`upscale_start`), 값도 소문자 영어 코드(`drop`, `click`). 화면 문구(한국어)는 바뀌므로 값으로 쓰지 않는다.
- **소음 줄이기:** 진행률, 마우스 움직임, 슬라이더의 모든 변화는 보내지 않는다. 슬라이더·미리보기는 카드마다 첫 조작 한 번만.
- **떠날 때:** `pagehide`와 컴포넌트 언마운트(사이트 안 이동) 둘 다에서 한 번만 보내고, `transport_type: "beacon"`을 붙인다.
- **깔때기 단계는 실제로 진행됐을 때만:** `add_*`는 하나라도 추가됐을 때만 보낸다. 전부 거부된 시도까지 보내면 "넣기" 단계가 부풀어 다음 단계 전환율이 낮게 보인다. 거부는 `*_rejected`가 맡는다.
- **사용자 행동과 정리 작업을 구분:** 페이지를 떠나며 코드가 남은 작업을 취소하거나 정리할 때는 `*_cancel` 같은 사용자 행동 이벤트를 보내지 않는다(PixelUp: 언마운트 때 `leaving` ref를 세우고 취소 이벤트를 건너뜀).
- **뒤로 가기 캐시:** 방문당 한 번 보내는 이벤트의 "보냄" 표시는 `pageshow`에서 `event.persisted`이면 초기화한다. bfcache로 복원된 페이지에서 이어진 사용은 새 방문처럼 센다.
- **이유 코드 전달:** 실패 이유는 오류 객체에 코드로 실어 보낸다(PixelUp: 워커의 `UserError(message, reason)` → `EngineError.reason`, 크기·배율 한도는 `imageProblem()`의 `reason`). 화면 메시지를 문자열 비교해 분류하지 않는다.
- **방침과 문서:** 새로 보내는 항목은 개인정보처리방침의 이용 통계 항목과 `DEPLOY.md` 이벤트 표에 함께 적는다.

## 3. GA 설정

- **맞춤 측정기준(이벤트 범위):** 보고서에서 나눠 볼 값만 등록한다. 표시 이름은 문자·숫자·공백·밑줄만 된다(`·` 같은 기호를 넣으면 저장이 안 되고, 다음 입력이 이름 칸에 이어 붙는다). 매개변수 칸에 이름을 입력한 뒤 다른 칸을 눌러 목록을 닫고 저장한다(Esc는 창 자체를 닫는다).
- **맞춤 측정항목:** 숫자 값(초, 장수). 측정 단위 목록(일반·통화·…·밀리초·초·분·시간)은 화면 좌표보다 `[role=option]` 텍스트로 찾아 누르는 편이 확실하다.
- **주요 이벤트:** 관리 → 데이터 표시 → 이벤트 → **최근 활동** 탭(지난 28일에 받은 이벤트)에서 이름 옆 별표로 지정한다. "주요 이벤트" 탭에는 기본 `purchase`만 보인다. **GA가 그 이벤트를 한 번 받은 뒤에야 목록에 나오고, 이름만으로 미리 만드는 메뉴는 없다.** 그래서 배포 뒤 데이터가 들어온 다음에 한다.
  - 그때까지는 지정할 이벤트(예: `upscale_done`, `download`, `zip_download`)를 `DEPLOY.md`나 메모리에 "남은 일"로 적어 두고, 다음에 GA 이야기가 나오면 먼저 확인한다.
  - 빨리 끝내고 싶으면 사용자에게 실제 사이트에서 한 번 끝까지(넣기 → 처리 → 받기) 해 보라고 권한다. 몇 시간 안에 이벤트가 목록에 나온다.
- **유입 깔때기:** 탐색 → 유입경로 탐색: 방문 → 넣기 → 시작 → 완료 → 받기. **데이터가 없어도 미리 만들 수 있다**(받지 않은 이벤트는 `이벤트 생성: "<이름>"` 줄로 고른다). 화면 순서는 [ga4-console.md](ga4-console.md)의 "유입경로 탐색 만들기"에 있다.
- **사용자에게 설명할 때:** "주요 이벤트", "깔때기"는 처음 듣는 사용자가 많다. 묻기 전에 무엇인지와 무엇을 알 수 있는지를 작은 예로 설명한다. 예: "방문 1,000명 → 이미지 추가 300명 → 확대 200명 → 다운로드 150명처럼, 어느 단계에서 가장 많이 빠지는지 보여 주는 표입니다." 주요 이벤트를 지금 지정할 수 없는 이유(GA가 아직 그 이벤트를 받지 않음)도 함께 말한다. 깔때기는 지금 만들 수 있다.
- 등록 전 데이터에는 맞춤 측정기준이 적용되지 않으므로, 코드를 배포하기 전에 미리 등록해 두는 것이 좋다.

## 4. 시험 방법 (GA 없이)

개발 서버에서 `gtag`를 가로채 이벤트를 모은다.

```js
window.__ev = [];
window.gtag = (...a) => { if (a[0] === "event") window.__ev.push([a[1], a[2]]); };
```

- 방문마다 한 번 보내는 이벤트는 로드 시점에 이미 지나갔으므로, 헤더 링크로 다른 페이지에 갔다 돌아와(클라이언트 이동) 컴포넌트를 다시 띄워 확인한다.
- 개발 모드에서는 React StrictMode 때문에 effect가 두 번 돌아 방문당 이벤트가 두 번 찍힌다. 배포 빌드에서는 한 번이다.
- 다운로드 링크는 캡처 단계 리스너에서 `preventDefault()`해 파일을 저장하지 않고 이벤트만 확인한다.
- `confirm()` 창은 `window.confirm = () => true`로 바꿔 막힘 없이 시험한다.
- 파일 입력은 `DataTransfer`로 채운다: 캔버스로 원하는 크기의 PNG를 만들고(`canvas.toBlob`), `const dt = new DataTransfer(); dt.items.add(file); input.files = dt.files; input.dispatchEvent(new Event('change', { bubbles: true }))`. 거부 이유를 보려면 이미지가 아닌 파일과 한도를 넘는 파일도 넣는다.
- 슬라이더(`input[type=range]`)는 네이티브 setter로 값을 바꾸고 `input` 이벤트를 보낸다: `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, v); el.dispatchEvent(new Event('input', { bubbles: true }))`.
- 같은 글자의 버튼이 여러 개면(예: "시작"이 3개) 글자로 고르지 말고 `find` → `ref`로 누른다.
- 페이지를 새로 불러오는 동작(헤더 링크로 전체 이동)을 일으키는 스크립트는 중간에 끊기고 반환값도 사라진다. 다시 실행하지 말고, 도착한 페이지를 확인한 뒤 새 호출에서 이어 간다. 가로챈 `gtag`와 `window.__ev`는 클라이언트 이동에서는 남지만 새로고침에서는 사라지므로 다시 설치한다.
- 약 45초를 넘는 스크립트는 도구가 시간 초과로 끊지만 페이지 안에서는 계속 돈다. 오래 걸리는 작업은 시작만 하고, 다음 호출에서 기다렸다가(`await new Promise(r => setTimeout(r, 20000))`) `window.__ev`를 읽는다.
- 배포 뒤에는 실제 사이트의 JS 조각에 새 이벤트 코드가 들어갔는지 확인한다(페이지가 불러오는 `/_next/static/**/*.js`를 내려받아 이벤트 이름으로 찾기).
- 보고할 때는 확인한 이벤트와 실제로 찍힌 값(예: `image_rejected {"reason":"too_large_side","side_bucket":">2048"}`)을 적고, 개발 서버에서 재현하지 못한 것(뒤로 가기 캐시 복원, 오류 대체 경로 등)은 "확인하지 못한 것"으로 따로 적는다.

## 5. 예시

PixelUp의 이벤트 표(`~/image_upscale/DEPLOY.md` "구글 애널리틱스에서 볼 수 있는 이벤트")와 SongToBars의 `src/scripts/barforge/app.js` `track()` 호출을 참고한다.
